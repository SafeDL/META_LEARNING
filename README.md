# 历史响应驱动的跨系统碰撞场景发现

本项目研究：已经测试过一些驾驶系统，知道它们在哪些交通场景中容易出事故；换成一个新系统后，能否利用这些历史经验，再结合少量新测试，更快找到它的碰撞场景？

主要实验让各种测试方法从同一批备选场景中挑选测试。驾驶系统负责开车，测试方法负责决定下一次测哪个场景。下面说明已经实际采用的实验设置和结果。

项目同时保留 [HighwayEnv](simulation/highway/README.md) 和 [MetaDrive](simulation/metadrive/README.md) 两个仿真平台。本文所列主实验使用 HighwayEnv；MetaDrive 的源码、场景配置、运行脚本和回归测试继续保留在工程中。

## 历史系统和新的被测系统

实验共有 20 个驾驶系统，按用途分为三组。“系统”指一份确定的控制器配置或一轮独立训练得到的策略；SUT 是“被测系统”的英文缩写。

| 用途 | 数量 | 在实验中做什么 |
|---|---:|---|
| 历史系统 | 8 | 先运行交通场景，保存是否碰撞、最小间距等结果，作为可学习的历史经验 |
| 开发系统 | 4 | 用于选模型、确定参数和检查流程，不作为最终结果的被测对象 |
| 新被测系统 | 8 | 用于正式比较；测试方法只能逐次获得已经查询过的结果 |

这些系统来自四类控制方法，每类有两条实现路线。每条路线各有一个历史版本和一个目标版本。

| 控制类别 | 两条实现路线 | 通俗解释 | 历史／开发／目标数量 |
|---|---|---|---:|
| 规则控制 | IDM＋MOBIL；FVDM＋换道规则 | 按跟车距离、速度差和换道规则驾驶 | 2／1／2 |
| 优化规划 | 线性化 MPC；非线性约束轨迹优化 | 预测未来一段行驶过程，再计算满足约束的控制动作或轨迹 | 2／1／2 |
| 搜索规划 | UCT 树搜索；确定性束搜索 | 展开若干可能的动作序列，比较后选择当前动作 | 2／1／2 |
| 学习策略 | PPO；DQN | 通过与仿真环境交互学习驾驶策略 | 2／1／2 |

8 个历史系统和 8 个目标系统都包含上表的八条路线。4 个开发系统分别采用 IDM＋MOBIL、线性 MPC、UCT 和 PPO，使用单独的配置或训练运行。完整名单见 [系统注册表](controllers/highway/catalog.py)。

新系统与历史系统的区别有两种。规则和规划系统使用预先登记的新配置，例如 IDM 的期望车速从 30 m/s 调到 32 m/s，期望跟车时间从 1.6 秒调到 1.4 秒；学习系统则独立初始化、从头训练。因此，通常的新系统测试考察的是版本或训练运行变化。另设“留一家族”实验，例如测试学习策略时，将整个学习家族从历史训练、历史先验和开发选参中排除，考察跨控制家族的迁移。

五个学习型对象为历史 PPO、历史 DQN、开发 PPO、目标 PPO 和目标 DQN，各自完成 4194304 次训练交互。它们使用共同的道路、观测、动作和奖励定义，训练、资格检查与最终测试的场景坐标分开。检查点依据独立资格检查选择，不依据最终碰撞发现结果选择。

全部 20 个系统在正式测试前都通过五项基本能力检查：正常跟车、可避免的前车制动、完整停车、合法换道和考虑邻道后车约束。

## 测什么交通场景

平台为 HighwayEnv，范围是高速公路上的决策与控制。下文的“被测车”指由被测驾驶系统控制的车辆。其初始车速范围为 18–34 m/s，约为 65–122 km/h。

| 场景 | 实际发生什么 | 主要改变哪些条件 |
|---|---|---|
| 前车制动 | 被测车正在跟车，前车开始连续刹车 | 初始间距 8–65 米、双方速度差、制动强度 2–9 m/s²，以及何时刹车、多久达到设定制动强度 |
| 邻车切入 | 左侧或右侧车辆连续横向移动，进入被测车前方 | 切入间距 5–50 米、速度差、切入时刻，以及横向移动时间 1.8–4 秒 |
| 前车切出暴露障碍 | 前车换到旁边车道，原本被挡住的静止障碍逐渐显露 | 跟车间距、前车速度、障碍位置 65–160 米，以及前车切出的时刻和持续时间 |
| 换道后车冲突 | 当前车道有慢车，邻道有快速接近的后车，被测车自行决定是否换道 | 当前前车的间距和速度、邻道后车间距 5–50 米及速度 22–38 m/s，同时改变邻道前方空间 |

参数组合必须满足物理可执行条件，例如前车切出时必须能避开障碍。完整参数范围和去重精度见 [场景定义](benchmark/scenarios.py)。换道由被测系统自主决定；合理选择不换道不算失效。

所有系统使用相同的车辆动力学、动作限幅和可见交通信息。仿真每秒更新 20 次，驾驶系统每秒决策 5 次；每次正式场景最多运行 10 秒，碰撞或驶出道路时提前结束。学习策略可以持续减速直到停车。前车遮挡障碍时，各系统都不能提前读取障碍信息；背景车脚本不操纵被测车。

## 一次测试任务怎样进行

一项任务由“一个新被测系统、一类功能场景、一种数据条件”组成。每项任务有 512 个有效候选场景，测试方法最多查询其中 128 次。

1. 利用允许使用的历史系统记录，学习哪些场景的测试结果有关联。
2. 所有方法先查询相同的 8 个初始化场景。这 8 次包含在 128 次预算中。
3. 根据已有反馈选择下一个场景，获得真实碰撞标签和安全测量，再继续选择，直到用完预算。
4. 用 5 个配对随机种子重复；同一重复中的不同方法使用相同候选库、初始场景和环境条件。在第 16、32、64、128 次查询处记录结果。

本方法会同时估计“当前这个场景是否容易碰撞”和“测完它以后，能否帮助后续选择”。前瞻最多考虑 5 次查询，每获得一次真实反馈就重新决策。在线阶段固定历史编码器，只更新概率后验和历史来源权重。选择器看不到目标系统的内部参数、身份或尚未查询的测试结果。

候选库实验会预先运行并封存目标场景库，比较算法时由隔离接口逐次揭示已查询结果。不同方法可以在相同真实反馈上重复比较；128 次是每种方法的查询预算。建库的真实仿真开销与回放时的算法计算开销分别记录。

五个随机种子用于重复测试选择过程，不代表五个新驾驶系统，也不等同于五次独立的环境随机重复。

## 三种数据条件和四组主实验

| 数据条件 | 历史经验与当前候选场景的关系 | 用途 |
|---|---|---|
| 历史坐标复用 | 历史系统测过这些参数组合，目标系统的结果对选择器仍未知 | 检查已有场景上的跨系统迁移 |
| 同分布新坐标 | 参数来自相同普通场景范围，但使用历史库中没有的新组合 | 主结果条件；新点的历史响应由冻结历史模型预测，不额外免费运行历史系统 |
| 留出的困难组合 | 例如小间距同时强制动，或邻道后车距离近且接近速度高；这些组合不进入历史和开发档案 | 检查历史支持不足时的表现 |

场景范围和困难组合在正式目标评测前冻结，不按目标碰撞率调整。四组主实验分别考察：整体发现数量及行为覆盖；历史来源不匹配与严格留一家族；参考版本通过、目标版本碰撞的新问题；各机制的作用和实际计算成本。来源替换实验保持背景历史库不变，只替换指定的一组来源。

候选库主实验共有 10880 项方法运行，包含整体比较、严格留一家族、来源替换和消融。独立连续搜索扩展允许算法自行提出新坐标，采用四个预先登记任务：IDM＋MOBIL／前车制动、线性 MPC／前车切出、UCT／邻车切入、PPO／换道后车冲突。连续扩展先完成 40 项开发运行，再完成 5 种方法 × 4 个任务 × 5 个种子的 100 项正式运行，每项实际调用 128 次；结果单独报告。

## 与哪些测试方法比较

| 候选库方法 | 它如何选择下一次测试 |
|---|---|
| 随机 | 随机挑选尚未查询的场景 |
| 空间填充 | 尽量分散选点，覆盖不同参数区域 |
| 历史危险排序 | 优先测试历史系统认为危险的场景 |
| 最相近来源＋目标残差 | 根据目标反馈寻找相近历史来源，再修正其预测 |
| Pooled-FT | 混合历史样本预训练，再用目标反馈微调 |
| 无历史 GP | 从目标反馈学习碰撞概率，不使用历史系统数据 |
| FSBO 碰撞适配 | 按历史系统分别学习共享深核代理，再用目标反馈微调；依据[已有 FSBO 论文](https://arxiv.org/abs/2101.07667)适配为碰撞分类 |
| 本方法 | 利用历史响应关联和目标反馈更新预测，并考虑一次查询对后续选择的影响 |

连续扩展比较本方法、随机、Indago、SAMOTA 和 DeepHyperion，保留各自的搜索机制。实现与适配约定见 [对比方法说明](methods/baselines/README.md)。

这些是当前已经实现和比较的方法。文献核查还识别出 ENS 主动搜索、RGPE 多来源加权迁移及相关场景排序方法，尚未加入现有比较；已有实验完成不等于相关基线已全部覆盖。

## 怎样评价

| 指标 | 通俗含义 | 如何解释 |
|---|---|---|
| 去重碰撞场景数 | 在预算内找到了多少种不同参数组合的碰撞 | 越多越好；使用预先固定的参数分组精度，同组只计一次，不等同于独立软件缺陷数 |
| 发现曲线及 AUC | 随着测试次数增加，累计发现多少碰撞；AUC 是各次查询后累计数的平均值 | 越高越好；既奖励找到更多，也奖励更早找到 |
| 首次碰撞查询位置 | 测了多少次才第一次找到碰撞 | 越少越早；预算用完仍未发现的运行保留为删失记录，使用限制平均查询数 RMST 汇总 |
| 行为覆盖 | 碰撞是否涉及不同对象、接触方向、被测车动作和事件阶段的组合 | 衡量发现的问题是否多样；还在各方法共同达到的碰撞数量范围内比较覆盖 |
| 版本新增碰撞 | 对应参考版本通过，但目标版本碰撞 | 检查版本变化或独立训练后出现的问题 |
| 历史集合特有碰撞 | 允许使用的历史系统全部通过，但目标系统碰撞 | 检查仅看该历史集合容易遗漏的问题；与“版本新增”分别统计 |
| 辅助安全测量 | 最小车间距、TTC（按相对运动估计的碰撞时间）和其他安全违反 | 说明危险程度；实际碰撞由真实碰撞事件判定，不用风险阈值代替 |
| 成本 | 历史获取、模型训练、目标适配、选例计算、初始化及仿真分别用了多少时间或调用 | 区分前期建设和在线开销，重叠计时不相加 |

新增碰撞标签需要真实参考系统结果支持。对新坐标额外重放历史系统时单独计费，不能仅凭历史模型预测就认定“全部历史系统通过”。

结果按目标的实现或训练谱系汇总，随机种子作为同一谱系内的重复；比较使用配对分层自助法区间，不把所有种子当作独立驾驶系统。零发现运行、测量缺失和删失记录均保留。

## 已完成的结果

同分布新坐标条件下，每种方法有 8 个目标 × 4 类场景 × 5 个种子，共 160 项运行。以下为平均值，三个指标均越高越好。

| 方法 | 去重碰撞数 | 发现 AUC | 行为覆盖 |
|---|---:|---:|---:|
| 随机 | 11.24 | 5.66 | 4.42 |
| 空间填充 | 13.87 | 7.47 | 5.10 |
| 历史危险排序 | 21.58 | 11.43 | 5.35 |
| 最相近来源＋残差 | 31.11 | 18.42 | 6.32 |
| Pooled-FT | 33.28 | 19.87 | 6.20 |
| 无历史 GP | 29.64 | 16.48 | 6.49 |
| FSBO 碰撞适配 | 36.06 | 20.74 | 6.41 |
| 本方法 | 33.04 | 19.54 | 6.76 |

本方法相对历史危险排序平均增加 11.47 个去重碰撞，配对 95% 区间为 [7.19, 15.95]；相对 FSBO 的差为 −3.01，区间为 [−5.51, −0.74]。行为覆盖相对 FSBO 的差为 0.34，区间为 [−0.03, 0.88]，较高均值尚不构成稳定覆盖优势。完整三条件、留家族、来源替换、消融、成本和统计见 [有限候选报告](results/gcrt/collision/report/report.md)。

连续扩展每种方法有 20 项运行，均值如下；四个代表任务的结果不与候选库结果合并。

| 方法 | 去重碰撞数 | 发现 AUC |
|---|---:|---:|
| 随机 | 6.15 | 2.83 |
| Indago | 2.70 | 2.06 |
| SAMOTA | 30.65 | 13.58 |
| DeepHyperion | 3.20 | 1.60 |
| 本方法 | 10.05 | 7.29 |

SAMOTA 的发现数均值更高，本方法减去 SAMOTA 的配对区间为 [−45.55, 0.20]；四任务总体差异存在较大不确定性。任务明细、删失统计和独立曲线见 [连续搜索报告](results/gcrt/collision/continuous/report/report.json)。

正式结果已完成独立轨迹、预算、标签、统计和成本复核，共核验 472 项统计比较、27 组 PNG／SVG／PDF 图表；原正式验收包含 102 项通过的回归检查。原始执行与逐项验收记录位于 `results/benchmark/collision/`；验收时的说明文字保留为[历史快照](results/benchmark/collision/documentation_snapshot_before_readme_migration.txt)，供追溯当时记录，当前说明维护在本 README。

## 运行

```powershell
conda activate metadrive
python -B -m pytest tests simulation/metadrive/tests -q -p no:cacheprovider
python -B -m benchmark.qualification
```

上面的测试命令同时检查主工程和 MetaDrive。本轮整理后共 239 项通过；环境与规划求解器的提示保留在测试输出中。

资格记录与轨迹位于 `results/benchmark/collision/qualification/`。`python -B -m controllers.highway.train` 从头训练历史及开发对象，通过后冻结训练配置，再训练最终目标；已有运行不会被自动覆盖。

`python -B -m benchmark.run_collision` 串联当前重建流程：等待或启动历史／开发训练、复核公共接口、冻结训练配置，再训练最终目标，并依次执行新响应采集、模型构建、开发验证、主实验、认证、报告及连续扩展。阶段原始退出码和日志写入 `results/gcrt/collision/pipeline/`；阶段失败会停止流程。`--resume` 复用相同代码与对象下已完成的阶段，系统文件锁阻止两个流程重复执行。

`python -B -m benchmark.build_collision_models core` 从历史与开发档案构建基础模型，`complete` 构建包含留类别和来源替换的完整矩阵。各方法也提供单独的构建入口，见对应目录说明。

分阶段命令、日志及复核入口见 [基准运行说明](benchmark/README.md)。方法的概率模型、训练和选例实现见 [主方法说明](methods/gcrt/README.md)。

## 论文与交流规范

先用具体驾驶情境说明研究问题，再介绍方法和指标；英文缩写首次出现时解释用途。区分历史系统、开发系统、最终目标与测试选择算法，区分版本变化和完整控制家族留出。结果同时说明测试预算、数据条件和统计单位，研究主张与已取得的证据保持一致。
